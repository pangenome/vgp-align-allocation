# **2. Background**

In reading this document you will find similarities to the previous 24/25 allocation cycle. This is because fundamentally our mission did not change: we support a vibrant community of users performing various types of data analyses. What has changed is demand. Our successes in the areas of genome assembly and infectious disease monitoring has brought us even more users. All this makes us even more dependent on fantastic resources provided by ACCESS-CI. Aside from that we have a new exciting research area that will dramatically benefit from this allocation: generation of whole genome alignments across hundreds of newly sequenced genomes. 

## **2.1. Why is Galaxy needed?**

Any biomedical data analysis requires (1) software tools, (2) computational infrastructure to run these tools, and (3) data (including data to be analyzed and/or reference datasets such as reference genome sequences etc.). If we look at each of these components separately, we will see that they are all seemingly available to any biomedical researcher. Indeed, due to strong open source tradition in biomedical research most analytical software tools can be readily obtained from sources such as BioConda, CondaForge, or BioContainers. Computational infrastructure is also readily accessible in many forms ranging from researcher’s own hardware to institutional clusters as well as commercial and public clouds. Finally, aside from data generated by researchers themselves, large open and controlled-access repositories containing millions of datasets are available via a number of international resources such as NCBI, EBI, UCSC Genome Browser and others. 

So if most data analytics components are available, what is the problem? The problem is that these components are disconnected. Despite the availability of individual components, only a fraction of biomedical researchers utilize them effectively (or even know they exist). Why is that? When data size and complexity (number of samples, experimental conditions, etc) is low, it is possible to analyze data on a local infrastructure such as one’s laptop. This is attractive because a user has full control of this computational environment. The immediate problem with this approach is that it tends to breed irreproducibility (each student/postdoc in a given lab will do analyses differently and few will record what they did, specify tool versions etc.). Furthermore, there is a general paucity of computational skills (e.g., basic UNIX shell skills, ability to compose and execute workflows etc.) among biomedical researchers [\[1\]](https://paperpile.com/c/AVr1OT/B1eHT). As data size and complexity grows two additional complications arise, further decreasing the number of researchers that can perform analyses. First, more sophisticated analyses require more tools. Different tools have distinct resource requirements (memory, CPUs, GPUs, etc.). To make such analyses tractable they need to be organized into workflows. This can be done using a variety of approaches ranging from simple bash scripts to comprehensive workflow languages (all open source) such as Nextflow, Snakemake, WDL, CWL and others. Second, larger datasets require high performance throughput infrastructure (HTC) that range from institutional clusters to virtualized private and public cloud environments. Running analysis in these environments requires yet another level of expertise that includes the ability to work with job scheduling systems (e.g., SLURM) and have working knowledge of container environments (Docker, Apptainer, Kubernetes, etc.). In other words, availability does not equal adoption. What prevents the adoption is the lack of an integrative environment that can orchestrate tool execution on appropriate resources and connect them to data. Such an environment should be capable of facilitating data analyses irrespective of a researcher’s computation skills. It needs to cater to different use scenarios (from graphical user interface \[GUI\] access to application programming interface \[API\]), analysis scales, and communities of practice (from experimental biologists to developers). The Galaxy Platform is such an environment. It is an ecosystem in which a biologist, a statistician, a population geneticist, a software developer, a system engineer, an educator and any other participant of biomedical research enterprise can find tools and features beneficial to the immediate goals of her/his research. It provides access to the latest data and tools deployed on modern computational infrastructure. Most importantly, we do not build such a system by ourselves. Instead, we are maintaining and growing a vibrant community of users and developers. This leads to continuing adoption of the system, ensures sustainability, and makes the system future-proof. If experience has taught us anything, it is that an open community is the key to the success of transformative efforts.

## **2.2. How is the Galaxy code organized?**

Galaxy is an integrative environment that orchestrates tool execution on appropriate resources and connects them to data. Achieving this in practice requires a number of components. Our team has been developing these components for almost two decades while continuously adapting them to changing technologies and hardware configurations. The components are numerous (the main GitHub repository for the project [\[2\]](https://paperpile.com/c/AVr1OT/qQ8yf) contains over 140 repositories) and discussing some of them is outside of the scope of this proposal. Instead, this section describes the most critical pieces of the machinery that makes Galaxy instances such as [htps://UseGalaxy.org](https://usegalaxy.org), the science gateway that utilizes the ACCESS resources in this proposal, work (Fig. 1). A Galaxy instance is a web application that allows users to upload their own data, access reference datasets, run analysis tools on these data, combine multiple tools into workflows, visualize or download results, or perform additional analyses using ad hoc analytics platforms such as Jupyter, RStudio, ObservableHQ etc. Galaxy can perform these operations at scale (e.g., with thousands of users analyzing thousands of datasets simultaneously), provide permanent and temporary storage for researchers analyzing their data, and interact with users either via GUI or API interfaces.

## **2.3. How does Galaxy run on ACCESS-CI resources?**

Code components described in the previous section are used to deploy Galaxy Instances. The largest of these instances, the US instance run on ACCESS-CI resources and housed at TACC [\[12\]](https://paperpile.com/c/AVr1OT/XPBEX), sustains \~4,000 simultaneous users at any given moment running on average \~50,000 jobs (distinct tool \[e.g.,  bwa, hifiasm\] executions) a day. Each user is provided with 250Gb of permanent storage and 2Tb of scratch storage allowing for analyses of large and complex datasets (total footprint of user data fluctuates around \~5Pb plus a growing amount of cold storage on tape). Storage quotas can be increased by explicit request from users. We were able to support such a large (and continuously growing; Fig. 2) user base by deploying Galaxy infrastructure on ACCESS-CI resources. The “head nodes” are deployed from the Texas Advanced Computing Center (TACC)—one of the world’s leading computational hubs [\[13\]](https://paperpile.com/c/AVr1OT/3cJVU). All required resources are procured using this allocation request. The system architecture for <https://usegalaxy.org> is shown in Fig. 2. Here, a set of virtual machines running web handlers, job handlers, a database server, a messaging queue server, as well as CVMFS Stratum 0 and Stratum 1 servers distributing reference data from the core of the system. From here Galaxy, using Pulsar (see 2.2 above)—a Python server application that allows a Galaxy server to run jobs on remote systems written by our group [\[14\]](https://paperpile.com/c/AVr1OT/BzGJk)—schedules computational jobs on remote resources with configured Pulsar endpoints. For extensive documentation of Galaxy system architecture see the production environment guide [\[15\]](https://paperpile.com/c/AVr1OT/0UBBs) a number of tutorials targeting system administrators [\[16\]](https://paperpile.com/c/AVr1OT/Uq1Ib). Because of Galaxy’s ability to distribute computational jobs across a wide variety of remote resources via the Pulsar network, we can map resource requirements of tools to available infrastructure. In other words, we can schedule memory intensive jobs on nodes with large amounts of RAM while jobs that are expected to be small will be sent to “generic” compute boxes, and jobs expecting GPU availability—to GPU nodes. This capability is provided by the Total Perspective Vortex (see 2.2 above, TPV) [\[17\]](https://paperpile.com/c/AVr1OT/4KDsu). TPV provides an administrator-friendly way to map individual tools to appropriate hardware destinations. For more complex cases, TPV also allows you to embed Python code into the configuration file and implement fine-grained control over jobs. Lastly, TPV offers a shared global database of default resource requirements. By leveraging this database, administrators do not have to figure out the requirements for each tool separately. The shared database is maintained and distributed via a Github repository.

## **3.2. Ongoing - Vertebrate Genome Project**

VGP is a global effort (phase 1 includes over 70,000 species with global distribution). As such the ability to analyze and assemble sequencing data must also have global reach. At this time VGP uses DNAnexus as the primary analysis environment. This effectively prevents utilization of VGP analysis workflows by the global community. The advances in sequencing technologies (such as HiFi approach from PacBio and further refinement of Oxford Nanopore Technology) allow assembly of human-sized genomes using machines with \~1Tb of RAM or less (For example, HiCanu, a state of the art genome assembly tool, can assemble a human genome in \~4,000 core hours with 128 GB of RAM. Peregrine can perform assembly in \~100 core hours with 500GB of RAM). The infrastructure available via ACCESS-CI allocations will allow us to keep up with the demand and, most importantly, create the first public resource allowing assembly of large genomes on the web\! **As of July 2025 we have assembled over 348 new vertebrate genomes using Galaxy workflows deployed on ACCESS-CI infrastructure (see** [**https://galayxproject.org/projects/vgp**](https://galayxproject.org/projects/vgp)**).** 

## **3.3. Ongoing - Computing whole genome alignments across hundreds of eukaryotic genomes**

Existing comparative genomic approaches (such as those stemming from generation of hundreds of genomes by efforts like VGP described above)  that are meant to scale to hundreds of eukaryote scale genomes are based on phylogenetic guide trees. The use of these guide trees can bias our ability to understand incomplete lineage sorting, which is of particular relevance to clades where rapid radiation obscures and complicates any direct phylogenetic analysis. In order to build an unbiased perspective on evolution across the vertebrate clade, we are using the Galaxy allocation on Stampede3 to compute a direct all-to-all alignment of the vertebrate genomes. Because the alignment task is fundamentally quadratic, this requires substantial resources that have been enabled by TACC. Our initial estimates, based on completion of 10% of the task, suggest that we will require around 5 million CPU hours to complete one iteration of the all-to-all alignment of 477 high quality genome assemblies. The indexes required for the initial homology mapping require around 7TB of disk space, which has been easy to achieve due to the flexible scratch storage on Stampede3. We estimate the output alignment will require around 10-15TB. In 2025 we have developed a robust set of workflows for generating alignments. These workflows will be put into production during the next allocation phase.

Given the large and active community currently using the main Galaxy instance, there is already very high demand for the additional resources and capabilities provided by ACCESS-CI. This is a projection based on current, awarded supplement, and expected usage. **Jetstream-2 Large Memory**: 12,000,000 SUs to enable assemblies of large genomes such as those of plants and animals with higher ploidy. These organisms have a genome that can be many fold larger than that of the human and require a large amount of RAM. Specifically, our Jetstream-based assembly-specific Galaxy instance at <https://vgp.usegalaxy.org> is utilizing these resources. **Galaxy is the only public resource allowing genome assembly. This is only possible because of our access to Jetstream-2 Large Memory instances. The demand for these resources will increase in 2025/26 allocation period.**

**Jetstream-2 GPU**: 200,000 SUs to enable running of tools providing native GPUs support. This is critically important for the whole genome alignment efforts that will be enabled by the Galaxy system. 

**TACC Stampede 3**: 500,000 SUs (node-hours) for long running parallel jobs. This is no change from the amount of our previous year’s request, and projected from our current usage. 

**PSC’s Bridges-2 Regular Memory**: 1,500,000 SUs for medium-memory assembly jobs, in particular genome and transcriptome assembly. 

**PSC’s Bridges-2 Expanded Memory**: 100,000 SUs for large-memory assembly jobs, in particular transcriptome assembly.

**SDSC Expanse**: 1,500,000 SUs to support additional capacity for generation of multiple-genome alignments. 

**SDSC Expanse GPU**: 100,000 SUs. This is critically important for the whole genome alignment efforts that will be enabled by the Galaxy system.

**NCSA Delta GPU**: 100,000 SUs. Same as above: This is critically important for the whole genome alignment efforts that will be enabled by the Galaxy system. In particular, access to H200 GPUs will enable utilization of the new alignment method published by us last year [\[19\]](https://paperpile.com/c/AVr1OT/Bb5p). 

**TACC Ranch**: 4 Pb for transitioning to tiered storage and decreasing our current Corral footprint.

**Purdue Anvil**: 1,500,000 SUs to support additional capacity for large-memory jobs when capacity is reached on Bridges-2, Expanse, and Stampede-3.

# **5. Metrics for success**

## **5.1. Continuous assessment and improvement**

To ensure that we are achieving maximum impact and not implementing solutions for problems that no longer exist, our entire team will engage in a continuous assessment approach. We will maintain a public list of the current roadmap and priorities. At least quarterly we will reevaluate these priorities in the context of current progress and the research environment and in consultation with users. We will use the metrics collected above to prioritize platform development.

## **5.2. Release process and updates**

Stable versions of Galaxy will be released two to three times a year. These releases follow a defined process, which begins by holding a meeting of the Galaxy committers team [\[20\]](https://paperpile.com/c/AVr1OT/VlUuT) to determine which pending pull requests and issues should be included or addressed in the upcoming release. Each release is assigned a release manager—a member of the Galaxy committers group who oversees the process. The release manager creates a Git branch for the new release and pushes it to  the Galaxy repository in Github during the month preceding the release. After this time, the release is frozen, and only bug fix (no new features) pull requests may be accepted against the release branch. One to two weeks after the creation of the release branch, the main public site is updated to the pending version, allowing for a controlled testbed of the new version in production. When the release manager, with the consultation of the committers team, is satisfied that no release-critical bugs remain, the new version is released and announced. Stable versions are frozen and can only receive bug fixes, new features are accepted to the “dev” branch.

## **5.3. Collaborative activity**

Our project is collaborative by design. In particular, the global usegalaxy.\* infrastructure is supported by groups in the US, EU and Australia, who procure their own funding but share all software components, tools, tutorials, workflows and other research and development products in a unified, collaborative framework. In addition to this activity we are leveraging expertise of providers of leading software components and databases. Our plan is to work with them on ensuring interoperation of our resources. We are also a major component of European Elixir [\[21\]](https://paperpile.com/c/AVr1OT/B1yR2) infrastructure. Recently we have been in talks with the CERN [\[22\]](https://paperpile.com/c/AVr1OT/8WemO) to join forces on the development of major infrastructure components such as shared filesystem (Galaxy already uses CVMFS developed by CERN; Fig. 10) and distributed computing approaches. We are expecting to further solidify these links as well as establish new collaborations with authors of emerging tools and databases. Our plan for the duration of this project is to use funds allocated during years 2, 3, and 4 to enable technology and software component transfer between the institutions and individuals listed in this section by connecting our software developers and by working on shared components. Through our outreach and training efforts we will identify and grow new collaborations with users and developers.   

## **5.4. Working with end-users**

Our continuous communication with end-users is enabled by Discourse-based help system [\[23\]](https://paperpile.com/c/AVr1OT/Xo4LC) and Gitter channels [\[24\]](https://paperpile.com/c/AVr1OT/CytLG) for conversational discussion. News is communicated primarily through Galaxy Newsletters and social media (BlueSky, LinkedIn, and Mastadon). Other communication channels include the Galaxy News feed, the Galactic Blog, and the Galaxy Events calendar, all of which are promoted on social media and in the newsletters (see [\[25\]](https://paperpile.com/c/AVr1OT/kfcRk)).
