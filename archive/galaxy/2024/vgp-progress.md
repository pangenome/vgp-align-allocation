# **BIO240121: Deploying vertebrate genome project (VGP) data from ACCESS resources: A pilot**

# **Progress report (2024 allocation period)**

During the 2024 allocation period, we initiated and completed the first phase of mirroring the Vertebrate Genomes Project (VGP) data hosted on Amazon S3. This initial effort resulted in the successful replication of approximately 1.2 petabytes of data, comprising over 3.4 million individual objects. Establishing a local copy of this expansive dataset not only enhances data accessibility and supports downstream analyses, but also significantly reduces reliance on commercial cloud infrastructure.

The mirrored dataset encompasses approximately 709 species, each represented by a rich assortment of genomic and bioinformatic file types. In total, more than 3.1 million files were cataloged, underscoring the comprehensive nature of the VGP's sequencing and annotation initiatives. The most prevalent file type is FASTA (148,001 files), highlighting a strong emphasis on reference genome assemblies. This is followed by FASTQ files (38,828), which reflect substantial raw sequencing output, and nearly equivalent numbers of GFF (38,825) and BAM (47,660) files, indicating extensive annotation and alignment efforts. Additional key file types include CRAM, SAM, and VCF, all contributing thousands of records related to variant calling and sequence alignment. Notably, more than 2.8 million files are categorized as “other,” likely representing a broad spectrum of analysis outputs, metadata, and non-standard formats.

## **What are our goals for the next allocation period**

As the VGP dataset continues to grow, ongoing synchronization will be essential to maintain the accuracy and completeness of our local mirror. To this end, we plan to implement a regular update schedule to efficiently capture changes and ensure long-term data integrity.

Using data stored on JetStream2 we will initiate the process of generation of multiple genome alignment using the Galaxy system. Specifically, we will focus on multiZ pipeline involving multiple steps performed by distinct command line utilities. The knowledge on using these tools largely exists “in-house” at Penn State and the UCSC Genomics institute. Our aim is to democratize these procedures and make them widely accessible. First we will address the two current known bottlenecks: repeatmasking and pairwise alignment components of existing pipelines by replacing them with modern high performance tools. We will then take a closer look at the pipelines themselves to identify and fix additional weak points. 

**Repeat masking.** Repeat masking is essential for performing efficient pairwise alignment. Traditionally it has been performed with RepeatMasker [\[1\]](https://paperpile.com/c/9Fp4Ht/gkiVD), which requires a species-specific library of interspersed elements. Such libraries are not available for newly sequenced genomes. We will instead use the Extensive *de novo* TE Annotator (EDTA;  [\[2\]](https://paperpile.com/c/9Fp4Ht/4qNsm); developed in Schatz's lab). 

**Pairwise alignment.** One major component and bottleneck of both alignment pipelines is the pairwise genome alignment tool lastZ [\[3\]](https://paperpile.com/c/9Fp4Ht/8i5Rk) based on the ‘Seed, Filter & Extend’ paradigm (see Fig. 2). Any improvements via GPUs have the potential to reduce the cost of these alignments dramatically. A replacement for lastZ is a GPU-accelerated version called SegAlign [\[4\]](https://paperpile.com/c/9Fp4Ht/eyJVb), which uses GPU to speed up the ‘Seed’ and ‘Filter’ stages and improves performance by a factor of 5-10✕. We found that, in SegAlign, there exists a significant issue of hardware underutilization. This underutilization frequently leads to the case where all hardware resources -both CPU and GPU -wait for a few CPU threads to complete their work. In extreme cases, a single CPU thread can work for over 66% of the total runtime while all other hardware resources–both CPUs and GPUs, stay idle. This problem cannot be fixed with more hardware resources; in fact, doing so exacerbates the problem by resulting in an even larger fraction of idling resources. We also observed that this underutilization is input-dependent; inputs with lower genetic distance are more affected by this problem, due to more work done for ‘gapped-alignment’ in the ‘extend’ stage resulting in a CPU bottleneck, rather than GPU. However, such inputs can also benefit from significant speedup using our proposed solution. We address this problem using two distinct methods; the first is restricting the maximum amount of work sent to a single CPU thread, that is, to the gapped-alignment stage of SegAlign which uses lastZ. This method directly increases CPU utilization by splitting a large unit of work among several threads. The second method is using a recent Nvidia GPU feature called Multi-Instance GPU (MIG) to physically partition a GPU, together with Multi-Process Service (MPS) which allows multiple processes to run concurrently on a GPU instance. Both allow multiple workloads to run in parallel within a single GPU. For this method, we split our genome inputs into blocks and run each pair of blocks with SegAlign in parallel using MIG + MPS, leading to higher CPU and GPU utilization in addition to hiding overheads–cases where GPU or CPU may become idle. We use these two methods together to obtain the best possible speedup for Whole Genome Alignment using SegAlign. On an A100 GPU with 32 cores we obtained up to 3✕ speedup, where in the best case we reduce runtime from \~36 hours to 11 hours when aligning the human (hs1) against chimpanzee (panTro6) genomes (Fig. 1).

**multiZ****-specific components.** The multiZ pipeline shown in Fig. 2 relies on two primary software components: lastZ and UCSC utilities. Both are packaged in BioConda and BioContainers and some (lastZ and fasplit) are already incorporated in Galaxy. In the initial phase of this task we will wrap tools for steps 4, 5, 6, 7, 8, and 9 into Galaxy. We will replace lastZ and the GPU-enabled SegAlign and assess performance gains. In particular our preliminary results indicate that the convoluted logic of genome “chunking” (Fig. 2, steps 2, 3, and 4), which currently partitions genome into segments and spawns thousands of lastz jobs across a cluster, can be replaced with a single within-a-node step (e.g., alignment runs shown in Fig. 1 are all performed within a single node). Finally, we will create an alternative version of the multiZ pipeline using a “modernized” set of UCSC utilities created by the group of Dr. Michael Hiller [\[5\]](https://paperpile.com/c/9Fp4Ht/BHSoP) that improves paralogy/orthology relationships and the alignment of coding exons [\[6\]](https://paperpile.com/c/9Fp4Ht/Qv6Cc), distributed as the Genome Alignment Tools [\[7\]](https://paperpile.com/c/9Fp4Ht/r8bQD) and Make\_LastZ\_Chains [\[8\]](https://paperpile.com/c/9Fp4Ht/kB2ZP), for an improved accuracy across larger phylogenetic distances.

| \*\*Figure 2.\*\* A schematic representation of the multiZ pipeline. Blue bars represent analysis steps performed by distinct tools. The workflow begins by softmasking interspersed and tandem repeats in the input genomes. The genomes are then split into smaller segments for parallelization purposes and all segments of the reference are aligned against all segments of each genome using lastZ. The resulting alignments are combined (in non-reference genome bins), sorted, and split by reference chromosomes. They are then chained and the chains are used to create nets. These steps are performed in parallel for each reference/genome{1, 2, …, \*N\*} combination. Subsequently all reference/genome combinations are combined into multiple alignments with multiZ. Resulting MAF datasets are used to define conserved regions identified by phastCons and to compute per-base phyloP values.. 2bit, lav, axt, psl, and MAF are various intermediate file formats (described in \[\\\[9\\\]\](https://paperpile.com/c/9Fp4Ht/80gVX)).  |
