# **2. Background**

In reading this document you will find similarities to the previous 25/26 allocation cycle. This is because fundamentally our mission did not change: we support a vibrant community of users performing various types of data analyses. What has changed is demand. Our successes in the areas of genome assembly and comparative genomics have brought us even more users, and the completion of Phase 1 of the Vertebrate Genomes Project has moved a large fraction of that community's analysis onto public infrastructure. All this makes us even more dependent on the resources provided by ACCESS-CI.

## **2.1. Why is Galaxy needed?**

Any biomedical data analysis requires (1) software tools, (2) computational infrastructure to run these tools, and (3) data (including data to be analyzed and/or reference datasets such as reference genome sequences etc.). If we look at each of these components separately, we will see that they are all seemingly available to any biomedical researcher. Indeed, due to strong open source tradition in biomedical research most analytical software tools can be readily obtained from sources such as BioConda, CondaForge, or BioContainers. Computational infrastructure is also readily accessible in many forms ranging from researcher's own hardware to institutional clusters as well as commercial and public clouds. Finally, aside from data generated by researchers themselves, large open and controlled-access repositories containing millions of datasets are available via a number of international resources such as NCBI, EBI, UCSC Genome Browser and others.

So if most data analytics components are available, what is the problem? The problem is that these components are disconnected. Despite the availability of individual components, only a fraction of biomedical researchers utilize them effectively (or even know they exist). Why is that? When data size and complexity (number of samples, experimental conditions, etc) is low, it is possible to analyze data on a local infrastructure such as one's laptop. This is attractive because a user has full control of this computational environment. The immediate problem with this approach is that it tends to breed irreproducibility (each student/postdoc in a given lab will do analyses differently and few will record what they did, specify tool versions etc.). Furthermore, there is a general paucity of computational skills (e.g., basic UNIX shell skills, ability to compose and execute workflows etc.) among biomedical researchers [1]. As data size and complexity grows two additional complications arise, further decreasing the number of researchers that can perform analyses. First, more sophisticated analyses require more tools. Different tools have distinct resource requirements (memory, CPUs, GPUs, etc.). To make such analyses tractable they need to be organized into workflows. This can be done using a variety of approaches ranging from simple bash scripts to comprehensive workflow languages (all open source) such as Nextflow, Snakemake, WDL, CWL and others. Second, larger datasets require high performance throughput infrastructure (HTC) that range from institutional clusters to virtualized private and public cloud environments. Running analysis in these environments requires yet another level of expertise that includes the ability to work with job scheduling systems (e.g., SLURM) and have working knowledge of container environments (Docker, Apptainer, Kubernetes, etc.). In other words, availability does not equal adoption. What prevents the adoption is the lack of an integrative environment that can orchestrate tool execution on appropriate resources and connect them to data. Such an environment should be capable of facilitating data analyses irrespective of a researcher's computation skills. It needs to cater to different use scenarios (from graphical user interface [GUI] access to application programming interface [API]), analysis scales, and communities of practice (from experimental biologists to developers). The Galaxy Platform is such an environment. It is an ecosystem in which a biologist, a statistician, a population geneticist, a software developer, a system engineer, an educator and any other participant of biomedical research enterprise can find tools and features beneficial to the immediate goals of her/his research. It provides access to the latest data and tools deployed on modern computational infrastructure. Most importantly, we do not build such a system by ourselves. Instead, we are maintaining and growing a vibrant community of users and developers. This leads to continuing adoption of the system, ensures sustainability, and makes the system future-proof. If experience has taught us anything, it is that an open community is the key to the success of transformative efforts.

## **2.2. How is the Galaxy code organized?**

Galaxy is an integrative environment that orchestrates tool execution on appropriate resources and connects them to data. Achieving this in practice requires a number of components. Our team has been developing these components for two decades while continuously adapting them to changing technologies and hardware configurations. The components are numerous (the main GitHub organization for the project [2] contains over 140 repositories) and discussing some of them is outside of the scope of this proposal. Instead, this section describes the most critical pieces of the machinery that makes Galaxy instances such as <https://usegalaxy.org>, the science gateway that utilizes the ACCESS resources in this proposal, work (Fig. 1). A Galaxy instance is a web application that allows users to upload their own data, access reference datasets, run analysis tools on these data, combine multiple tools into workflows, visualize or download results, or perform additional analyses using ad hoc analytics platforms such as Jupyter, RStudio, ObservableHQ etc. Galaxy can perform these operations at scale (e.g., with thousands of users analyzing thousands of datasets simultaneously), provide permanent and temporary storage for researchers analyzing their data, and interact with users either via GUI or API interfaces.

**Figure 1.** Components of the Galaxy ecosystem and external dependencies. The upper portion shows GitHub [2] repositories of key Galaxy components. The lower portion lists some of the most important external projects. For more information about individual components see Table 1.

The core functionality is contained within the /galaxy repository. The main application is managed by a process manager, /gravity. Galaxy schedules jobs (e.g., if a user maps reads then, for example, bwa-mem jobs will be scheduled this way) on remote resources via the /pulsar application and manages resource allocations using /total-perspective-vortex (e.g., bwa jobs can be scheduled on a conventional cluster node, while, say, hifiasm jobs—genome assembly requiring large memory—will be routed to nodes with high RAM or, ColabFold [3] jobs will be directed to nodes with attached GPUs). Galaxy provides users with a unified repository of reference data stored in CVMFS [4]. This repository allows data synchronization across all Galaxy instances and other systems. Galaxy provides access to thousands of analysis tools. The tool ecosystem is managed by the Intergalactic Utilities Commission, which maintains a repository with Galaxy tools (/tools-iuc) and operates the project's "app store," called the ToolShed [5]. Tool development is facilitated with the Planemo SDK ([6]; /planemo). Production Galaxy instances deploy tools as Singularity containers by drawing them directly from BioContainers [7], which, in turn, depends on BioConda [8] and CondaForge packages. Galaxy also maintains a growing repository of high quality analysis workflows (/iwc) maintained by the Intergalactic Workflow Commission (IWC). These workflows are also distributed via Dockstore and WorkflowHub portals in the US and EU, respectively. Finally, Galaxy contains an extensive portfolio of dissemination and training components. These include the /training-material repository—a community resource behind our main training site [9]. Because training events in data science performed using Galaxy often require substantial computational resources (e.g., imagine running a workshop for 50 people on genome assembly) we developed a dedicated Training-Infrastructure-as-a-Service (TIaaS [10]; /tiaas2) framework. It allows trainers to reserve a dedicated job execution queue on our public resources. This eliminated wait time for workshop participants making training events highly effective. The Galaxy main website is managed from the /galaxy-hub repository.

## **2.3. How does Galaxy run on ACCESS-CI resources?**

Code components described in the previous section are used to deploy Galaxy instances. The largest of these instances, the US instance run on ACCESS-CI resources and housed at TACC [12], sustains thousands of simultaneous users at any given moment. Each user is provided with 250 GB of permanent storage and 2 TB of scratch storage allowing for analyses of large and complex datasets. Storage quotas can be increased by explicit request from users. We were able to support such a large (and continuously growing; Fig. 2) user base by deploying Galaxy infrastructure on ACCESS-CI resources. The "head nodes" are deployed from the Texas Advanced Computing Center (TACC)—one of the world's leading computational hubs [13]. All required resources are procured using this allocation request. The system architecture for <https://usegalaxy.org> is shown in Fig. 2. Here, a set of virtual machines running web handlers, job handlers, a database server, a messaging queue server, as well as CVMFS Stratum 0 and Stratum 1 servers distributing reference data form the core of the system. From here Galaxy, using Pulsar (see 2.2 above)—a Python server application that allows a Galaxy server to run jobs on remote systems written by our group [14]—schedules computational jobs on remote resources with configured Pulsar endpoints. For extensive documentation of Galaxy system architecture see the production environment guide [15] and a number of tutorials targeting system administrators [16]. Because of Galaxy's ability to distribute computational jobs across a wide variety of remote resources via the Pulsar network, we can map resource requirements of tools to available infrastructure. In other words, we can schedule memory intensive jobs on nodes with large amounts of RAM while jobs that are expected to be small will be sent to "generic" compute boxes, and jobs expecting GPU availability—to GPU nodes. This capability is provided by the Total Perspective Vortex (see 2.2 above, TPV) [17]. TPV provides an administrator-friendly way to map individual tools to appropriate hardware destinations. For more complex cases, TPV also allows one to embed Python code into the configuration file and implement fine-grained control over jobs. Lastly, TPV offers a shared global database of default resource requirements. By leveraging this database, administrators do not have to figure out the requirements for each tool separately. The shared database is maintained and distributed via a GitHub repository.

**Figure 2.** Architecture of Galaxy component deployment on ACCESS-CI/TACC resources. Here, a Galaxy server consisting of a series of virtual machines (VMs; left) interacts with the outside world via web handlers. Job handlers distribute computational jobs on any remote system using Pulsar—a remote scheduler [14].

## **3.2. Ongoing — Vertebrate Genomes Project**

VGP is a global effort (phase 1 includes over 70,000 species with global distribution). As such the ability to analyze and assemble sequencing data must also have global reach. The advances in sequencing technologies (such as the HiFi approach from PacBio and further refinement of Oxford Nanopore Technology) allow assembly of human-sized genomes using machines with ~1 TB of RAM or less. The infrastructure available via ACCESS-CI allocations allows us to keep up with the demand and, most importantly, sustain the first public resource allowing assembly of large genomes on the web. As of [TODO: month] 2026 we have assembled [TODO: N] new vertebrate genomes using Galaxy workflows deployed on ACCESS-CI infrastructure (see <https://galaxyproject.org/projects/vgp>). The trajectory of this effort is itself the argument for the request: over 150 assemblies as of July 2024, 348 by July 2025, and 417 by October 2025. These assemblies span genome sizes from ~1 Gb to over 3 Gb with contig N50 values between 40 Mbp and 355 Mbp, often encompassing complete chromosomes and chromosome arms. The methods underlying this work are published [27].

Two developments during the 2025/26 period change the scale of this work. First, we are completing Phase 1 of the VGP and are preparing a series of publications under that umbrella that feature ACCESS-CI infrastructure—specifically Jetstream2—as the enabling platform for hundreds of reference-quality assemblies produced reproducibly within Galaxy. Second, we deployed GenomeArk2 (<https://genomeark2.org>), described below, which moves both the data and its downstream analysis onto public infrastructure.

## **3.3. Ongoing — GenomeArk2: a unified distribution platform for VGP data**

To strengthen data accessibility and long-term sustainability, we developed GenomeArk2 (<https://genomeark2.org>) as the central distribution hub for VGP data. This resource serves as the authoritative repository for reference assemblies, annotations, and downstream analysis results generated through the VGP and related initiatives. Built on top of Jetstream2's scalable object storage, GenomeArk2 provides fast, open access to petabyte-scale datasets while ensuring robust metadata support, versioning, and reproducibility. Its architecture integrates with Galaxy and other community analysis systems, allowing researchers to discover, access, and process VGP data directly within public computational environments. By coupling open compute with open data distribution, GenomeArk2 establishes a model for transparent, FAIR (Findable, Accessible, Interoperable, and Reusable) genomics data dissemination.

This is the direct rationale for the Jetstream2 storage component of this request: the object store is not scratch space but the public face of a community data resource. We are placing particular emphasis on encouraging the global genomics community to perform large collaborative analyses on public research infrastructure rather than commercial clouds. This increases the return on investment in national computing resources by demonstrating their effectiveness for large-scale, cost-efficient genomic research.

## **3.4. Ongoing — Computing whole genome alignments across hundreds of eukaryotic genomes**

Existing comparative genomic approaches that are meant to scale to hundreds of eukaryote-scale genomes are based on phylogenetic guide trees. The use of these guide trees can bias our ability to understand incomplete lineage sorting, which is of particular relevance to clades where rapid radiation obscures and complicates any direct phylogenetic analysis. In order to build an unbiased perspective on evolution across the vertebrate clade, we are computing a direct all-to-all alignment of the vertebrate genomes. Because the alignment task is fundamentally quadratic, this requires substantial resources.

Our estimate, based on completion of 10% of the task, is that one iteration of the all-to-all alignment of 477 high-quality genome assemblies requires approximately 5 million CPU hours. The indexes required for the initial homology mapping require around 7 TB of disk space, and we estimate the output alignment will require 10–15 TB. During 2025 we developed a robust set of workflows for generating these alignments; during the 2025/26 period these workflows moved into production. # **5. Metrics for success**

## **5.1. Continuous assessment and improvement**

To ensure that we are achieving maximum impact and not implementing solutions for problems that no longer exist, our entire team engages in a continuous assessment approach. We maintain a public list of the current roadmap and priorities. At least quarterly we reevaluate these priorities in the context of current progress and the research environment and in consultation with users. We use the metrics collected above to prioritize platform development.

## **5.2. Release process and updates**

Stable versions of Galaxy are released two to three times a year. These releases follow a defined process, which begins by holding a meeting of the Galaxy committers team [20] to determine which pending pull requests and issues should be included or addressed in the upcoming release. Each release is assigned a release manager—a member of the Galaxy committers group who oversees the process. The release manager creates a Git branch for the new release and pushes it to the Galaxy repository on GitHub during the month preceding the release. After this time, the release is frozen, and only bug fix (no new features) pull requests may be accepted against the release branch. One to two weeks after the creation of the release branch, the main public site is updated to the pending version, allowing for a controlled testbed of the new version in production. When the release manager, in consultation with the committers team, is satisfied that no release-critical bugs remain, the new version is released and announced. Stable versions are frozen and can only receive bug fixes; new features are accepted to the "dev" branch.

## **5.3. Collaborative activity**

Our project is collaborative by design. In particular, the global usegalaxy.* infrastructure is supported by groups in the US, EU and Australia, who procure their own funding but share all software components, tools, tutorials, workflows and other research and development products in a unified, collaborative framework. In addition to this activity we are leveraging expertise of providers of leading software components and databases. Our plan is to work with them on ensuring interoperation of our resources. We are also a major component of European ELIXIR [21] infrastructure. We have been in talks with CERN [22] to join forces on the development of major infrastructure components such as shared filesystems (Galaxy already uses CVMFS developed by CERN) and distributed computing approaches. We expect to further solidify these links as well as establish new collaborations with authors of emerging tools and databases. Through our outreach and training efforts we identify and grow new collaborations with users and developers.

## **5.4. Working with end-users**

Our continuous communication with end-users is enabled by a Discourse-based help system [23] and chat channels [24] for conversational discussion. News is communicated primarily through Galaxy Newsletters and social media (Bluesky, LinkedIn, and Mastodon). Other communication channels include the Galaxy News feed, the Galactic Blog, and the Galaxy Events calendar, all of which are promoted on social media and in the newsletters (see [25]).
